# Plan: Consistent create endpoint responses and card activity query in Application

- **Branch:** `fix/api_inconsistencies`
- **Status:** Done
- **Date:** 2026-11-12
- **Requirements:** [api-create-responses.md](../feature-requirements/api-create-responses.md)

## Goal
Every API endpoint that adds a new item answers 201 Created with the address of the new item, as
adding a card or a participant already does, and the card activity query sits in the application
layer next to the similar queries. This fixes the first two parts of finding L9 of the main branch
code review.

## Scope
- In scope:
  - FR-1 to FR-5: the 17 create endpoints that answer 200 today answer 201 Created, with a
    `Location` header where the item has its own address; the OpenAPI document and the
    front-end's generated types are updated.
  - Refactor without behaviour change: move `CardActivityQuery` from
    `Monthwise.Infrastructure` to `Monthwise.Application`.
- Out of scope:
  - **L9 third part, `GetCardHandler` loads everything to return one card.** Its predecessor is
    review finding **H4** (per-request reuse of loaded ledgers), which is not started. The
    per-request caching of H4 removes most of this cost, so it is done after H4 is merged, or
    dropped if H4 already solves it. It is not touched on this branch.
  - Endpoints that change existing items and the bulk actions (requirements, section 5).

## Design
- Domain / data model changes: none.
- API changes (endpoints, DTOs):
  - Replace `.ToOk()` by `.ToCreated(location)` (the existing helper in
    `ResultHttpExtensions`) on these endpoints, with the `Location` of FR-3:

    | Endpoint | Location |
    |---|---|
    | `POST /api/inputs` | `/api/inputs/{id}`; for a recurring input `/api/recurring-inputs/{recurringInputId}` |
    | `POST /api/input-categories` | `/api/input-categories/{id}` |
    | `POST /api/cards/{id}/balance-entries` | `/api/balance-entries/{entryId}` |
    | `POST /api/loans` | `/api/loans/{loan.id}` |
    | `POST /api/loans/{id}/payment-changes` | `/api/loans/{id}/payment-changes/{changeId}` |
    | `POST /api/loan-categories` | `/api/loan-categories/{id}` |
    | `POST /api/loan-categories/{id}/subcategories` | `/api/loan-subcategories/{subId}` |
    | `POST /api/card-purchases` | `/api/card-purchases/{purchase.id}` |
    | `POST /api/revolving-cards/{id}/extra-payments` | `/api/extra-payments/{paymentId}` |
    | `POST /api/revolving-cards/{id}/debt-entries` | `/api/debt-entries/{entryId}` |
    | `POST /api/expense-categories` | `/api/expense-categories/{id}` |
    | `POST /api/recurring-bills` | `/api/recurring-bills/{id}` |
    | `POST /api/bills?month=` | `/api/bills/{id}` |
    | `POST /api/expenses` | `/api/expenses/{id}` |
    | `POST /api/expenses/cash-withdrawals` | `/api/expenses/cash-withdrawals/{id}` |
    | `POST /api/card-issuers`, `POST /api/banks` | none (no item address) |

  - For card issuers and banks, add a `ToCreated` overload without a location
    (`TypedResults.Created()` with no URI), so the answer is 201 without `Location`.
  - Loan payment change: the body stays `LoanDetailsResponse`. To know the new change's id,
    `PaymentChangeHandler.CreateAsync` returns it next to the details (for example a small
    `Result<(LoanDetailsResponse Details, Guid ChangeId)>`, or the endpoint finds it from the
    domain's `AddChange` result passed out of `ChangeAsync`); the body sent to the client is only
    `LoanDetailsResponse`.
  - Request and response DTOs do not change (FR-2); error answers do not change (FR-4).
  - The OpenAPI document `backend/openapi/monthwise.json` is regenerated by the build and
    committed (CI checks it is up to date).
- Application layer refactor (no behaviour change):
  - Move `CardActivityQuery` from
    `Monthwise.Infrastructure/Persistence/Repositories/CardRepositories.cs` to
    `Monthwise.Application/Cards/CardActivityQuery.cs`. It only uses `LoanLedger`,
    `CardPaymentLedger` and `RevolvingLedger`, which are Application classes.
  - Keep the `ICardActivityQuery` interface and its use in `GetCardsHandler` unchanged; move the
    `AddScoped<ICardActivityQuery, CardActivityQuery>()` registration from Infrastructure's
    `DependencyInjection` to Application's.
- Front-end changes (pages, components): none in pages. Regenerate `frontend/src/api/schema.d.ts`
  (`npm run api:generate`). `openapi-fetch` treats every 2xx answer as data and `unwrap` checks
  `response.ok`, so the API calls keep working; check the TypeScript build for any type that
  named the `200` response.
- Database migrations: none.

## Steps
1. Add the `ToCreated` overload without location to `ResultHttpExtensions`.
2. Switch the 17 create endpoints to `ToCreated` with the locations above (Cash flow, Loans, Card
   purchases, Revolving, Expenses, Cards endpoint files).
3. Return the new change id from `PaymentChangeHandler.CreateAsync` for the payment change
   location.
4. Move `CardActivityQuery` to Application and its DI registration.
5. Build the API to regenerate `openapi/monthwise.json`; regenerate the front-end schema types.
6. Update the API tests (below); run back-end and front-end builds, linters and tests.

## Tests
- Unit tests: none new; the moved query is covered by the existing card list tests.
- API / integration tests:
  - Update every API test that adds an item and expects 200 to expect 201, including the two
    helpers that accept "200 or 201" (`RevolvingEndpointTests`, `SharedCostEndpointTests`),
    which now expect 201 only.
  - New test: for each create endpoint, 201 Created and a `Location` header with the expected
    address (acceptance 1 and 2); one check that the `Location` of a new bill, loan and
    payment change answers on GET/PUT.
  - New test: adding a card issuer or bank answers 201 without `Location` (acceptance 3).
  - Existing validation, 404 and 409 tests stay unchanged and keep passing (acceptance 4).
  - `ArchitectureTests` keep passing after the move.
- Manual checks: in the running app, add an input, a bill, an expense, a cash withdrawal, a loan,
  a payment change, a card purchase, a balance entry, an extra payment, a debt entry, one of each
  category and a card issuer and bank; each one is saved and shown as before (acceptance 6).
