# Plan: Name comparison ignoring upper/lower case

- **Branch:** `fix/name-comparison`
- **Status:** Draft
- **Date:** 2026-11-11
- **Requirements:** [name-comparison.md](../feature-requirements/name-comparison.md)

## Goal
"Unique, ignoring upper/lower case" means exactly one thing in every name list, defined once in
the database, so names with č, ć, ž, š, đ behave predictably on every installation (code review
finding L3).

## Scope
- In scope: every name list with a `lower(name)` unique index (card, card_issuer, bank, payer,
  input_category, loan_category, loan_subcategory, loan, purchase_category, expense_category,
  recurring_bill, participant), their repository checks, the payer lookup used on the fly (FR-4),
  `RecurringInputRepository.AddSkip` (synchronous `.Any()`), restore of backups (FR-7).
- Out of scope: accent-insensitive matching, sorting and the payer search box (both stay in
  C#), login and households. Error mapping of other unique indexes (finding L12).

## Design
- Domain / data model changes: none in the domain. The name rule (FR-1) is defined once, as a
  PostgreSQL ICU collation `monthwise_name` (`provider = icu`, `locale = 'und-u-ks-level2'`,
  `deterministic = false`): case-insensitive, accent-sensitive, independent of the database's own
  locale (NFR-1). PostgreSQL 17 (all deployments) supports it.
- Infrastructure:
  - `MonthwiseDbContext.OnModelCreating`: `modelBuilder.HasCollation("monthwise_name", locale:
    "und-u-ks-level2", provider: "icu", deterministic: false)`; each name column above gets
    `.UseCollation("monthwise_name")` in its configuration (one shared extension
    `HasNameCollation()` in `Persistence/Configurations`, so the collation name lives in one place).
  - Repositories: `NameInUseAsync` / `FindByNameAsync` compare `c.Name == name` and let the
    database apply the column collation (FR-2). The `ToLowerInvariant`/`ToLower()` code and its
    `#pragma` suppressions go away.
  - `PayerRepository.FindByNameAsync` still checks payers added earlier in the same request
    (`db.Payers.Local`). It uses one helper, `NameComparison.Equals(a, b)`
    (`CompareInfo.Invariant` with `CompareOptions.IgnoreCase`, the same ICU root level-2 rule),
    with a comment tying it to the collation; a unit test pins that both agree on the test names.
  - `AddSkip` becomes `AddSkipAsync` and uses `AnyAsync`; the two callers in
    `RecurringInputHandlers` and `InputHandlers` await it.
  - Restore (`HouseholdDataStore`): rows are written through the same tables, so a backup with
    two same-name entries hits the unique index inside the restore transaction; it is mapped to
    the "not a valid export file"-style refusal with a message naming the list (FR-7), and the
    current data is kept (the transaction rolls back).
- API changes (endpoints, DTOs): none. Duplicate names keep returning the existing
  *name already in use* problem response.
- Front-end changes (pages, components): none.
- Database migrations: one migration `UseNameCollation`:
  1. Pre-check (FR-6): one `DO $$ ... $$` block that, per table, looks for groups of names equal
     under `monthwise_name` (respecting the same partial `WHERE` and the subcategory's
     `category_id`) and `RAISE EXCEPTION` with the table and the names. The migration runs in a
     transaction, so nothing is changed; startup shows the existing "could not be brought up to
     date" response and the log says what to rename.
  2. `CREATE COLLATION monthwise_name ...` (generated by `HasCollation`).
  3. `ALTER COLUMN name TYPE ... COLLATE monthwise_name` for each table.
  4. Drop each `ux_*_name_lower` index and create `ux_*_name` on `(name)` (with the same partial
     `WHERE` / `category_id`), so the index uses the column collation.
  5. `Down` reverses 4, 3 and 2.
  The seed `UPDATE ... WHERE lower(name) = ...` statements in old migrations are left alone.

## Steps

   on the latest `main`.

3. Add the migration with the pre-check, collation, column and index changes; check the
   generated snapshot.
4. Switch all repository name checks to plain equality; add `NameComparison` for the payer

5. Map a unique-name failure during restore to the refusal of FR-7.
6. Add the tests below; run `dotnet build`, `dotnet test` (with `MONTHWISE_TEST_DB`) and the
   front-end checks to confirm nothing else changed.

## Tests
- Unit tests: `NameComparison.Equals` for *Čevapi/čevapi/ČEVAPI* (equal), *Čaj/Caj*, *Đak/Dak*
  (different), plain ASCII.
- API / integration tests (real database, NFR-3):
  - For each name list: adding and renaming to *ČEVAPI* while *Čevapi* exists returns the usual
    *name already in use* response; *Caj* next to *Čaj* is accepted (acceptance 1, 2).
  - New input with payer *ana* while *Ana* exists reuses *Ana* (acceptance 3).
  - Closed loan *Đak* does not block *đak*; open one does (acceptance 4).
  - Migration pre-check: a database at the previous migration with *Čevapi* and *čevapi* in one
    list fails the migration with a message naming the table and both names, and the data is
    unchanged; without duplicates, all rows are kept (acceptance 6, 7).
  - Restore of a backup with two same-name entries is refused and current data is kept (FR-7).
  - Test database created with `--locale C` as well as the default, so the result does not depend
    on the database locale (acceptance 5).
- Manual checks: add *Čevapi* then *čevapi* as an expense category in the running app and see the
  usual message.
