# Plan: Name comparison ignoring upper/lower case

- **Branch:** `fix/name-comparison`
- **Status:** In progress
- **Date:** 2026-11-11
- **Requirements:** [name-comparison.md](../feature-requirements/name-comparison.md)

## Goal
"Unique, ignoring upper/lower case" means exactly one thing in every name list, defined once in
the database, so names with č, ć, ž, š, đ behave predictably on every installation (code review
finding L3).

## Scope
- In scope: every name list with a `lower(name)` unique index (card, card_issuer, bank, payer,
  input_category, loan_category, loan_subcategory, loan, expense_category, recurring_bill,
  participant; purchase categories are expense categories since the bills feature), their repository checks, the payer lookup used on the fly (FR-4),
  `RecurringInputRepository.AddSkip` (synchronous `.Any()`), restore of backups (FR-7).
- Out of scope: accent-insensitive matching, sorting and the payer search box (both stay in
  C#), login and households. Error mapping of other unique indexes (finding L12).

## Design
- Domain / data model changes: none in the domain. The name rule (FR-1) is defined once, as a
  PostgreSQL ICU collation `monthwise_name` (`provider = icu`, `locale = 'und-u-ks-level2'`,
  `deterministic = false`): case-insensitive, accent-sensitive, independent of the database's own
  locale (NFR-1). PostgreSQL 17 (all deployments) supports it.
- Infrastructure:
  - `Persistence/NameCollation.cs` holds the rule in one place: the collation name and locale,
    `HasNameCollation()` (called in `MonthwiseDbContext.OnModelCreating`), `UseNameCollation()`
    for each name column, and `AreSame(a, b)` for the in-memory checks below.
  - The unique indexes are now declared in the configurations (`ux_<table>_name`, with the same
    partial filter for loans and recurring bills, and `(category_id, name)` for subcategories)
    instead of hand-written SQL.
  - Repositories: `NameInUseAsync` / `FindByNameAsync` compare `c.Name == name` and let the
    database apply the column collation (FR-2). The `ToLowerInvariant`/`ToLower()` code and its
    `#pragma` suppressions go away.
  - `PayerRepository.FindByNameAsync` still checks payers added earlier in the same request
    (`db.Payers.Local`). It uses `NameCollation.AreSame(a, b)`
    (`CompareInfo.Invariant` with `CompareOptions.IgnoreCase`, the same ICU root level-2 rule); a
    test pins that it agrees with the database collation on the test names.
  - `AddSkip` becomes `AddSkipAsync` and uses `AnyAsync`; the two callers in
    `RecurringInputHandlers` and `InputHandlers` await it.
  - Restore (`HouseholdDataStore`): the file check that runs before anything is replaced (both
    for *Check file* and *Import*) also runs `SameNameCheck` over the file's rows with
    `NameCollation.AreSame`, scoped like the indexes. Two same-name entries refuse the file with
    the new `data.same_names` field error naming the list and both names (FR-7); the current data
    is not touched. Files of older releases are checked the same way.
- API changes (endpoints, DTOs): none. Duplicate names keep returning the existing
  *name already in use* problem response.
- Front-end changes (pages, components): none.
- Database migrations: one migration `UseNameCollation`:
  1. `CREATE COLLATION monthwise_name ...` (generated by `HasCollation`).
  2. Pre-check (FR-6): one `DO $$ ... $$` block that, per table, looks for groups of names equal
     under `monthwise_name` (respecting the same partial `WHERE` and the subcategory's
     `category_id`) and raises a `unique_violation` naming the table and the names. The
     migration runs in a transaction, so nothing is changed; startup shows the existing "could
     not be brought up to date" response and the log says what to rename.
  3. Drop each `ux_*_name_lower` index.
  4. `ALTER COLUMN name TYPE ... COLLATE monthwise_name` for each table.
  5. Create `ux_*_name` on `(name)` (from the model), so the index uses the column collation.
  6. `Down` drops the new indexes, resets the columns, recreates the `lower(name)` indexes and
     drops the collation last.
  The seed `UPDATE ... WHERE lower(name) = ...` statements in old migrations are left alone.

## Steps
1. Wait for L6 (database tests no longer skipped silently) to be merged, then rebase this branch
   on the latest `main`.
2. Add the collation, the `HasNameCollation()` extension and the column configuration.
3. Add the migration with the pre-check, collation, column and index changes; check the
   generated snapshot.
4. Switch all repository name checks to plain equality; use `NameCollation.AreSame` for the
   payer in-request check; make `AddSkip` async (`AddSkipAsync` with `AnyAsync`).
5. Check the backup file for same-name entries before restoring (FR-7).
6. Add the tests below; run `dotnet build`, `dotnet test` (with `MONTHWISE_TEST_DB`) and the
   front-end checks to confirm nothing else changed.

## Tests
- Agreement test: `NameCollation.AreSame` and the database collation give the same answer for
  *Čevapi/čevapi/ČEVAPI*, *Ćevapčići*, *Đak/đAK*, *Žana*, *Štedionica*, *Ana* (same) and
  *Čaj/Caj*, *Đak/Dak*, *Ćup/Čup*, *Ana/Ana M.* (different).
- API / integration tests (real database, NFR-3):
  - For each name list: adding and renaming to *ČEVAPI* while *Čevapi* exists returns the usual
    *name already in use* response; *Caj* next to *Čaj* is accepted (acceptance 1, 2).
  - New input with payer *ana* while *Ana* exists reuses *Ana* (acceptance 3).
  - Closed loan *Đak* does not block *đak*; open one does (acceptance 4).
  - Migration pre-check: a database at the previous migration with *Čevapi* and *čevapi* in one
    list fails the migration with a message naming the table and both names, and the data is
    unchanged; without duplicates, all rows are kept (acceptance 6, 7).
  - Restore (check and import) of a backup with two same-name entries, of this and of an older
    release, is refused with the names and current data is kept (FR-7).
  - The migration test uses a database created with `LOCALE 'C'` (where the old `lower()` indexes
    let *Čevapi* and *čevapi* both in), and also reverts the migration. The whole suite was run
    against a default and a C-locale database (acceptance 5).
- Manual checks: add *Čevapi* then *čevapi* as an expense category in the running app and see the
  usual message.
